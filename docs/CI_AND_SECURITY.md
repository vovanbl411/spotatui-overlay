# CI, безопасность и восстановление

[Путь кандидата](AUTOMATION.md) · [Установка и откат](../README.md)

## Что проверяется и когда

| Когда | Что выполняется |
| --- | --- |
| PR в `main` (`pull_request`) | [Repository CI](../.github/workflows/ci.yml) проверяет предлагаемое изменение. Фильтр относится к целевой ветке PR. |
| Изменение `main` (`push`) | Те же проверки выполняются на принятой ветке, в том числе после ручного merge. Для профиля Release это требует [пункт V1 стандарта](https://github.com/vovanbl411/gentoo-overlay-standard/blob/15601aaac42493e30b80ce52b61a4a90f0446721/STANDARD.md#v1). Push в feature-ветку сам по себе CI не запускает. Обновление PR в `main` может запустить проверку через событие PR. |
| Подготовка кандидата до Publish | [Релизный workflow](../.github/workflows/prepare-release.yml) выполняет unit-тесты и при наличии кандидата вне dry-run проверяет его источники, Cargo-контракт, CRATES, Manifest и метаданные Gentoo. |
| Приёмка владельцем до merge | Сверяются точный PR head, результаты Prepare и CI. На Gentoo отдельно проверяются resolver, сборка и выбранные runtime-сценарии. |

Repository CI состоит из двух заданий.

- **Python automation** запускает unittest discovery по `scripts/test_*.py`
  и сверку CRATES с Manifest.
- **Gentoo package metadata checks** запускает `pkgcheck scan` для оверлея
  с `--profile default/linux/amd64/23.0 --exit` в Gentoo-контейнере.

Успех Repository CI подтверждает эти проверки для ревизии checkout.
Для события `pull_request` обычный checkout берёт тестовый merge ref.
Проверка resolver и сборки при приёмке относится к точному PR head.
Для кандидата откройте сводку и логи конкретных run и attempt из Draft PR.
Проверьте, какие шаги прошли. Пропуск Publish после dry-run, отсутствие
нового релиза и ошибка подготовки имеют разные причины и результаты.
Отчёт Prepare не подтверждает полную сборку и работу клиента.

## Права и границы записи

Repository CI получает `contents: read`. В релизном workflow по
умолчанию `permissions: {}`. Prepare получает `contents: read` и
`pull-requests: read`, а Publish — `contents: write` и
`pull-requests: write`. Все checkout отключают сохранение credentials.
Actions закреплены полными SHA, образы Gentoo — digest. При смене
пинов проверяйте поведение новой версии отдельно.
[Repository CI](../.github/workflows/ci.yml) · [Релизный workflow](../.github/workflows/prepare-release.yml)

Publish разрешён только в `vovanbl411/spotatui-overlay` для
`refs/heads/main` из `.github/workflows/prepare-release.yml@refs/heads/main`,
по расписанию или ручному запуску вне dry-run. Код берётся из
`github.workflow_sha`, который должен совпасть с `github.sha`.
Prepare может загружать артефакт в Actions и писать сводку. Права на
запись ветки и PR появляются только у Publish. ID и digest из
успешного Prepare связывают ZIP с этим run и attempt. Publish проверяет
его независимо и создаёт только отсутствующий ref и Draft PR.
Существующие ветки автоматически не изменяются, не удаляются
и не переиспользуются. Слияние выполняет владелец вручную.
[Допуск в Publish](../scripts/publish_release.py#L52) · [Проверка передачи](AUTOMATION.md#handoff--три-файла-и-доказательства)

## Настройки GitHub

При принятии оверлея владелец подтверждает, что `main` — default branch
и что её защита удерживает принятое состояние под его контролем.
Сверьте применимые rulesets и legacy protection, права участников
и bypass, защиту от удаления и неконтролируемого push или force-push,
ручное слияние через PR и выбранные required checks. Для каждого
required check подтвердите точное имя, источник и выполнение на PR.
Имена существующих jobs приведены в разделе о Repository CI.
Выбор обязательных проверок относится к решению владельца.
[Требования G1–G3](https://github.com/vovanbl411/gentoo-overlay-standard/blob/15601aaac42493e30b80ce52b61a4a90f0446721/STANDARD.md#политика-github)

В настройках Actions проверьте, разрешены ли закреплённые Actions,
может ли Publish получить нужные разрешения `GITHUB_TOKEN` и
разрешено ли Actions создавать PR. GitHub для PR, созданных или
обновлённых с помощью `GITHUB_TOKEN`, ставит запуски `pull_request`
по `opened`, `synchronize` и `reopened` в ожидание одобрения.
Пользователь с правом записи запускает их через
**Approve workflows to run**. Перед принятием смотрите фактическое
состояние проверок на нужном head.
[Поведение событий GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

**Наблюдение от 27 ноября 2026 года.** Публичный API для `main`
вернул `protected=false` и пустой список required status checks.
Списки правил для ветки и rulesets репозитория в публичном ответе
пусты. Административные параметры Actions, возможность создания
Draft PR с `GITHUB_TOKEN`, эффективные права участников и bypass
остаются **UNKNOWN** до проверки владельцем. Hosted-запуск пути
Phase 4.4 в рамках этой проверки не проводился.

## Диагностика и восстановление

Начните с первого отказавшего шага в Actions и соответствующей сводки.
Зафиксируйте run, attempt, SHA базы и, если есть, SHA кандидата.
При остановке Publish найдите последнее подтверждённое действие
и сверьте его с состоянием ветки и PR на GitHub. Ветка может остаться
после сбоя, даже если job завершился ошибкой.

| Сбой | Где смотреть и что делать |
| --- | --- |
| Ошибка API на Discover | Смотрите HTTP-статус и шаг поиска релиза, истории PR или тега. В репозиторий ещё ничего не записано. Временный сбой чтения допускает повтор после восстановления API. Некорректный ответ сначала разберите. |
| Provenance архива | В `Source verification` сравните URL, SHA тега, Git-комментарий PAX, структуру tar и размер с хешами принятой базы. Пока расхождение не объяснено, публикация заблокирована. |
| Изменение Cargo-контракта | В `Cargo contract` найдите версию, лицензию, feature или зависимость, вызвавшую остановку. Нужны ревью upstream diff и решение по упаковке. Повтор с тем же содержимым проблему не устранит. |
| Версия или checksum pycargoebuild | В `CRATES generation and integrity` проверьте версию модуля, флаги и отказ скачивания или сверки с lock. Непроверенная версия и неверный хеш требуют выяснения причины. Ничего не публикуется. |
| Manifest не сходится | В `Manifest generation` и `Manifest verification` сравните состав distfiles, записи fallback, размер и хеши архива и crate в `DISTDIR`. До устранения причины Publish не допускается. |
| Ошибка pkgcheck | Смотрите диагностику временного оверлея и профиль `default/linux/amd64/23.0`. Исправьте применимую проблему упаковки или входные условия проверки. Обязательная ошибка блокирует готовность. |
| Handoff или readiness не совпали | Сверьте успешность Prepare, ID, SHA-256, ZIP, базу, run и attempt. Артефакт мог уже появиться в Actions, но ветки ещё нет от этого запуска. Если причина устранена и удалённой записи не было, нужен новый полный прогон от актуальной базы. Изолированный повтор Publish со старым ZIP не пройдёт проверку attempt. |
| Устарела удалённая `main` | Сверьте наблюдаемый SHA с базой из сводки. До push нужен новый Prepare на актуальном `main`. Если база сменилась после push, ветка уже создана. Переходите к ручному восстановлению. |
| Уже есть ветка или конфликтующий PR | Сверьте ref, SHA, историю точного head и открытые PR на тот же релиз. До push запись отсутствует. После push мог появиться новый конфликт. Наличие ветки или прежнего PR требует решения владельца, повтор его не обходит. Ошибка чтения ref не означает его отсутствия. |
| Неоднозначный push | Publish делает read-only lookup и не отправляет POST. Сравните наблюдаемый ref и SHA со сводкой. Даже точное совпадение SHA не доказывает принадлежность ветки запуску. Нужна ручная проверка. |
| Ветка создана, но PR отсутствует | Найдите подтверждение `Branch creation confirmed` и первый отказ после него. Ветка могла остаться. Проверьте её SHA, базу и всю историю PR перед ручным решением. |
| Неоднозначное создание PR | Проверьте сводку read-only lookup по точному head. Если PR найден, сверяйте номер, статус Draft, base, SHA и данные запуска. Отсутствие PR в ответе пока не подтверждает отсутствие записи. Повторять POST автоматически нельзя. |

Для проверки удалённого состояния подставьте версию из сводки вместо
`X.Y.Z`. Первая команда выводит SHA существующих refs без fetch и без
изменения checkout. Вторая читает публичный REST API без токена,
включая закрытые PR с точным head. Заголовок `Link` в ответе указывает
на другие страницы, если их нужно просмотреть. Ошибку доступа или
лимит API нельзя трактовать как пустой список.

```sh
version='X.Y.Z'
branch="automation/spotatui-v${version}"
git -c credential.helper= ls-remote --refs https://github.com/vovanbl411/spotatui-overlay \
  refs/heads/main "refs/heads/$branch"
curl --disable --fail --silent --show-error --include --get \
  --data-urlencode 'state=all' --data-urlencode "head=vovanbl411:$branch" \
  https://api.github.com/repos/vovanbl411/spotatui-overlay/pulls
```

При возможной записи владелец сначала сверяет принадлежность ветки,
head, родителя и Git tree с проверенным кандидатом, затем актуальный
`main` и конфликты. Если ветка подтверждена, база актуальна и конфликтов
нет, владелец может закончить публикацию вручную через Draft PR.
Если ожидаемый PR уже существует, продолжите проверку в нём. Устаревшая база или
чужая ветка требуют отдельного решения. Автоматизация не восстанавливает
ветки, не записывает повторно и не обходит закрытые PR.

## Приёмка владельцем

1. Сверьте точный head PR, целевую `main`, родителя коммита и diff.
   Проверьте upstream release notes, изменения Cargo, ebuild и Manifest.
   Сопоставьте SHA базы, handoff и результаты Prepare с конкретной
   попыткой. Проверьте результаты CI на том же head.
2. На тестовом Gentoo подключите отдельную рабочую копию этого PR.
   В ней `git rev-parse HEAD` должен совпадать с SHA из PR.
   Команда `emerge -pv media-sound/spotatui::spotatui-overlay` показывает
   план без установки. Сверьте версию, репозиторий, профиль, USE и
   зависимости. Это проверка resolver.
3. Соберите точного кандидата из исходников с заявленными USE и
   проверьте запуск, вход и воспроизведение Spotify через ALSA.
   Для включённых возможностей выполните относящиеся к ним проверки,
   например MPRIS в сеансе D-Bus, визуализацию с PipeWire или
   воспроизведение локального файла. Зафиксируйте ревизию, профиль,
   архитектуру, USE и результат каждого сценария. Установка binpkg
   сама по себе не подтверждает компиляцию из исходников.
4. После применимых проверок примите PR ручным слиянием и проверьте CI
   на обновлённой `main`. Если head сменился, перепроверьте новый diff
   и результаты для нового SHA.

### Открытые задачи упаковки

- **Минимальная версия Rust.** В ebuild задано `RUST_MIN_VER="1.91.0"`.
  При разборе `0.49.0` в lock найден `stream-download 0.24.6` с
  `rust-version = "1.95.0"`, хотя upstream-приложение заявляет
  `1.90`. Нужно определить фактический минимум для выбранных
  features и подтвердить его сборкой. Сравнение `rust-version`
  приложения не проверяет минимумы всех crate.
- **libclang для визуализатора.** В цепочке PipeWire у `pipewire-sys`
  и `libspa-sys` сборочные скрипты используют `bindgen`.
  Принятый ebuild не задаёт отдельной сборочной зависимости для
  libclang. Нужно проверить обнаружение библиотеки в чистом Gentoo
  и согласовать зависимость и её условие по USE. Исследование цепочки
  не подтверждает сборку с `visualizer`.

Эти задачи описывают результаты анализа упаковки. Изменения
Rust minimum и libclang в этой ревизии не внесены.
